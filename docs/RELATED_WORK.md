# GitHub benchmark review and project changes

The projects below informed this repository's **evaluation design**. Their reported profits cannot be compared numerically with ours because demand traces, network topology, reward accounting, constraints and action spaces differ. No external code or model weights were copied.

| Project | Relevant practice | What applies here |
| --- | --- | --- |
| [gym-invmgmt-paper](https://github.com/r2barati/gym-invmgmt-paper) | M5-style data adapter and common benchmark scenarios for learned, heuristic and optimization policies | Require the same sales trace, simulator and KPI definitions for all of our policies; keep source and model checksums. |
| [VN2 inventory planning](https://github.com/MatiasAlvo/vn2) | Direct policy-performance optimization and classical base-stock / newsvendor-style comparators | Our episodic CEM actor already optimizes whole-portfolio simulated return; we added an independently implemented quantile-based replenishment rule. We do not implement VN2's differentiable optimizer. |
| [Inventory Control with MPC and RL](https://github.com/jjalcaraz-upct/inventory-control) | Receding-horizon optimization and RL evaluated on common stochastic scenarios | Motivated auditing the allocator under the same frozen policies and replay conditions. Our new exact solver is a one-day score optimizer, **not** this project's MPC. A true horizon planner would need to model all 64 SKUs and shared constraints. |
| [Google OR-Tools knapsack example](https://github.com/google/or-tools/blob/stable/ortools/sat/samples/multiple_knapsack_sat.py) | Exact constrained assignment rather than a greedy packing heuristic | Motivated a small independent NumPy dynamic program for our four pack sizes. No OR-Tools code or runtime is copied. |
| [OR-Gym](https://github.com/hubbs5/or-gym) | Explicit inventory dynamics, lead times, lost sales and OR comparisons | Keep environment accounting transparent and preserve negative baselines; our existing accounting audit verifies the published replays. |

The immediate improvements prompted by this review were a [predeclared future-calendar check](NEW_TIME_HOLDOUT_PLAN.md) and a [stronger quantile safety-stock comparator](SAFETY_STOCK_BASELINE.md). The check loads the already released WI_1 and TX_3 bundles, verifies the official M5 evaluation file, continuously replays through day 1941, and scores **only** the previously unused days 1914–1941. The [frozen-policy results](NEW_TIME_HOLDOUT_RESULTS.md) and [safety-stock comparison](SAFETY_FUTURE_RESULTS.md) are published without retuning those bundles. A new 28-day window offers evidence across time, although it is too short to establish robust future performance or deployment readiness.

The M5 source files remain outside Git. The [Kaggle M5 data page](https://www.kaggle.com/competitions/m5-forecasting-accuracy/data) describes `sales_train_evaluation.csv` as extending through day 1941 and marks the dataset subject to its competition rules; the [Zenodo record](https://zenodo.org/records/10203108) provides the downloadable mirror and checksum. Dataset use does not turn observed sales into unconstrained demand or synthetic economics into actual retailer costs.

The later [exact-allocation audit](EXACT_ALLOCATOR_PLAN.md) fixes its comparison protocol before replay but is explicitly retrospective: both M5 test windows had already been inspected. It tests whether the existing greedy allocator maximizes a frozen policy's own one-day score and whether an exact score choice changes simulated profit. Under the current uniform unit-cost and unit-space assumptions, budget and capacity reduce to one bound on total order units, so this does not claim to solve a general two-resource inventory problem. [Results](EXACT_ALLOCATOR_RESULTS.md).
